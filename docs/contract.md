# Network Contract

Peer Watchalong uses JSON control messages over WebSocket and binary chunk
messages over WebRTC DataChannels. The tracker never carries video bytes.

## Shared fields

| Field | Type | Meaning |
| --- | --- | --- |
| `version` | `1` | Contract version |
| `type` | string | Message discriminator |
| `messageId` | string | Unique ID of this control message |
| `sessionId` | string | Room ID generated by the host |
| `timestamp` | number | Sender-local Unix time in milliseconds |
| `senderId` | string | Tracker-assigned peer ID; used after registration |
| `replyTo` | string | `messageId` of the request being answered |

Every response has its own `messageId` and a `replyTo`. An `ERROR` has
`replyTo` when it rejects a specific request. The tracker verifies `senderId`
against the WebSocket connection and never trusts it by itself.

## Registration

The host generates a unique `sessionId`. The tracker assigns all peer IDs,
including the host's.

### `CREATE_ROOM_REQ`

Host to tracker. Sent before the host has a peer ID.

```ts
{
  version: 1;
  type: 'CREATE_ROOM_REQ';
  messageId: string;
  sessionId: string;
  timestamp: number;
  payload: {};
}
```

The tracker rejects a duplicate `sessionId` with `SESSION_ALREADY_EXISTS`.

### `CREATE_ROOM_RES`

Tracker to host.

```ts
{
  replyTo: string;
  payload: {
    assignedPeerId: string;
    topology: PeerTopology; // Layer 0
  };
}
```

### `JOIN_ROOM_REQ`

Viewer to tracker. The viewer supplies the host-generated `sessionId` and has
no peer ID yet.

```ts
{
  version: 1;
  type: 'JOIN_ROOM_REQ';
  messageId: string;
  sessionId: string;
  timestamp: number;
  payload: {};
}
```

### `JOIN_ROOM_RES`

Tracker to viewer.

```ts
{
  replyTo: string;
  payload: {
    assignedPeerId: string;
    hostPeerId: string;
    topology: PeerTopology;
  };
}
```

## Topology

```ts
interface PeerTopology {
  layer: 0 | 1 | 2 | 3 | 4 | 5;
  parents: string[];
  children: string[];
  siblings: string[];
}
```

Only tracker-authorized neighbors may signal or exchange chunks.

## Chunk discovery

| Message | Direction | Payload |
| --- | --- | --- |
| `CHUNK_HAVE_EVENT` | Peer to tracker | `{ chunkIndex: number }` |
| `CHUNK_QUERY_REQ` | Peer to tracker | `{ chunkIndex: number }` |
| `CHUNK_QUERY_RES` | Tracker to peer | `{ chunkIndex: number, holderIds: string[] }` |

`CHUNK_QUERY_RES.replyTo` references the query request. Returned holders must
be active, authorized neighbors that claim to have the chunk. An empty
`holderIds` array is a valid response.

## WebRTC signaling

| Message | Payload |
| --- | --- |
| `SIGNAL_SDP` | `{ targetPeerId, description: { type, sdp } }` |
| `SIGNAL_ICE` | `{ targetPeerId, candidate: { candidate, sdpMid, sdpMLineIndex } }` |

The tracker relays signaling only between authorized neighbors. These are
relayed messages, not request/response pairs, so they do not use `replyTo`.

## Errors

```ts
{
  type: 'ERROR';
  replyTo?: string;
  payload: {
    code: ErrorCode;
    message: string;
  };
}
```

Error codes are `INVALID_MESSAGE`, `NOT_REGISTERED`,
`SESSION_ALREADY_EXISTS`, `SESSION_NOT_FOUND`, `PEER_NOT_FOUND`,
`NOT_NEIGHBOR`, `INVALID_CHUNK`, `SESSION_FULL`, and
`PROTOCOL_VERSION_UNSUPPORTED`.

## DataChannel messages

Each message is one `RTCDataChannel.send()` call. Multi-byte integers are
unsigned 32-bit big-endian values.

```text
byte 0      opcode
bytes 1-4   requestId
bytes 5-8   chunkIndex
bytes 9+    chunk bytes for PAYLOAD only
```

| Opcode | Message | Size |
| ---: | --- | ---: |
| `0x01` | `REQUEST` | 9 bytes |
| `0x02` | `PAYLOAD` | 9-byte header plus chunk bytes |
| `0x03` | `NOT_AVAILABLE` | 9 bytes |

`PAYLOAD` and `NOT_AVAILABLE` repeat the request's `requestId` and
`chunkIndex`. `NOT_AVAILABLE` means the peer responded but lacks the chunk; a
timeout means no response was received.

Packets with unknown opcodes, invalid sizes, or an empty `PAYLOAD` are
rejected.
